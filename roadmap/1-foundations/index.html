About this phase

Phase 1 gives you a first, hands-on pass through every layer of a GPU system, from the Linux node up to Kubernetes. Each lab is the simplest useful version of one skill the job needs. The goal is breadth: after ten labs, no topic in an interview will be completely new to you.

Most labs run on your laptop or on one spot GPU for an hour or two. Where real hardware is expensive, you practise on a faithful stand-in first: Soft-RoCE instead of an InfiniBand fabric, a Redfish mockup instead of a real BMC, Slurm in Docker with fake GPUs instead of a cluster.

Every lab leaves a small artifact in your repository: a triage script, an XID decoder with tests, a DCGM report, an nccl-tests plot, a working GPU pod. Those artifacts become your study notes and, later, your proof.

What you'll learn, module by module

Each module is one topic. Read what it covers, skim the primer, then do its labs top to bottom.

Module 1ALinux and containers1 lab · 5 hRead the primer

The first-minute commands for a slow node and the USE method (utilization, saturation, errors) behind them. You create each bottleneck yourself so you recognise it.

  1. A1The 60-second node triage drillLearn the first commands you run on any slow node, and what each one rules out. You will create each bottleneck yourself, so you know what it looks like. Core5 hL
Module 2BGPU health and diagnostics2 labs · 11 hRead the primer

How the NVIDIA driver reports GPU faults (XID codes), which ones mean reset, reboot or replace, and how DCGM diagnostic levels 1–3 prove a GPU is healthy.

  1. B1Build an XID decoderXID errors are how the NVIDIA driver reports GPU problems in the kernel log. You will build a tool that reads them and tells an operator what to do. No GPU needed. Core5 hL
  2. B2DCGM diagnostics, levels 1 to 4DCGM is NVIDIA's data-center GPU manager. Its diag levels are how fleets prove a GPU is healthy. Learn what each level runs and how long it takes. Core6 hG1
Module 3KLLM and training literacy1 lab · 8 hRead the primer

The arithmetic customers ask about: memory per parameter, KV-cache size, training FLOPs and GPU-hours. No model training, just numbers you can defend.

  1. K1Transformer and cluster arithmeticInfrastructure people must do the math customers ask about: does the model fit, how big is the KV cache, how many GPU-days. You'll build a notebook you can reuse in interviews. Core8 hL
Module 4CServer hardware and topology1 lab · 5 hRead the primer

What sits inside a multi-GPU server: CPU sockets, NUMA nodes, PCIe switches, NICs and NVLink, and how to read nvidia-smi topo -m.

  1. C1Draw the node from memoryKnow which GPU sits next to which CPU socket and NIC. Every performance discussion (NUMA, GPUDirect, NCCL) starts from this picture. Core5 hG4
Module 5DBMC and out-of-band1 lab · 5 hRead the primer

Redfish, the REST API every modern server BMC exposes: power, sensors, event logs and firmware, practised on a mockup server.

  1. D1Redfish 101 on a mockup serverRedfish is the REST API every modern server BMC exposes (power, temps, fans, logs, firmware). You'll learn it with no hardware using DMTF's mockup server. Core5 hL
Module 6ERDMA and interconnect1 lab · 6 hRead the primer

What RDMA is (queue pairs, memory registration, verbs) and how to test it, using Soft-RoCE between two VMs.

  1. E1RDMA from zero on Soft-RoCERDMA lets one machine write into another's memory without the remote CPU. It's what InfiniBand/RoCE/EFA give NCCL. Soft-RoCE emulates it in software on any NIC, so you learn the commands and concepts for free. Core6 hV
Module 7FNCCL and collectives1 lab · 6 hRead the primer

What NCCL does, how to run nccl-tests and why busbw (not algbw) is the number to compare with link bandwidth.

  1. F1nccl-tests on one node and the busbw formulaNCCL is the library that moves data between GPUs for training. nccl-tests measures it. Learn to run it, read algbw vs busbw, and plot results. Core6 hG4
Module 8GSlurm and provisioning1 lab · 6 hRead the primer

Daily Slurm: partitions, sbatch/srun/squeue/sacct, and how GPUs are declared as GRES so jobs get only the GPUs they asked for.

  1. G1Slurm in Docker with fake GPUsSlurm is the HPC scheduler used for most large training clusters. Learn the daily commands and how GPUs are declared (GRES) on a laptop. 6 hL
Module 9HKubernetes for GPUs1 lab · 6 hRead the primer

What NVIDIA's GPU Operator installs on a Kubernetes node, in what order, and how to check each piece when a GPU pod won't start.

  1. H1GPU Operator on one nodeOn Kubernetes, NVIDIA's GPU Operator installs everything a node needs for GPUs. Learn what it deploys, in what order, and how a pod gets a GPU. Core6 hG1

By the end you can

  • Triage a slow Linux node in a minute and explain what each tool rules out
  • Decode XID errors and run DCGM diagnostics levels 1-3
  • Draw a GPU node's PCIe/NUMA topology and read nvidia-smi topo
  • Use Redfish, Soft-RoCE RDMA, nccl-tests, Slurm GRES and the GPU Operator at a basic level
  • Do the memory, KV-cache and FLOPs maths customers ask about

How the phase runs

  1. Week 1

    Laptop labs: node triage (A1), the XID decoder (B1) and the cluster arithmetic (K1). No cloud spend.

  2. Week 2

    First GPU sessions: draw a real node's topology (C1), run DCGM diagnostics (B2). Redfish on a mockup (D1) in between.

  3. Week 3

    Moving data: RDMA on Soft-RoCE (E1) and nccl-tests on a 4-GPU node (F1).

  4. Week 3–4

    Schedulers: Slurm in Docker (G1) and the GPU Operator on one node (H1). Then the checkpoint.

Tips

  • Read the topic primer before each module's first lab; it takes five minutes.
  • Group the GPU labs (C1, B2, F1, H1) so one instance serves two labs in an evening.
  • Write the interview answer in your own words in notes/<lab>.md before opening the model answer.
