The roadmap

Five phases, in order

Each phase has a goal, the labs grouped by topic, and a checkpoint to pass before you move on.

  1. 0

    Phase 0

    Set up your lab

    One evening of setup that every later lab reuses.

    Every later lab assumes three things: a Linux shell on your laptop, a cloud account that cannot surprise you with a bill, and Terraform files that create and destroy each lab environment in minutes. This phase builds all three once, so the rest of the roadmap is about learning, not plumbing.

    What you'll learn in this phase
    • A Linux workstation on Windows. WSL2 Ubuntu 24.04 with Docker, kind, kubectl, helm and k9s: the same tools you will use against real clusters.
    • Cloud guard-rails. A separate lab account, MFA, a budget alarm, a region choice and GPU quota requests for both On-Demand and Spot (they are different quotas).
    • Infrastructure as code for labs. Terraform templates for VMs, a GPU spot instance and two EFA nodes in a cluster placement group, reached through SSM instead of open SSH ports.
    • Cost discipline. Spot first, destroy every night, check for leftovers. Plus free and cheap alternatives for GPU time.

  2. 1

    Phase 1 · Beginner

    Foundations

    Touch every layer of a GPU system once.

    Phase 1 gives you a first, hands-on pass through every layer of a GPU system, from the Linux node up to Kubernetes. Each lab is the simplest useful version of one skill the job needs. The goal is breadth: after ten labs, no topic in an interview will be completely new to you.

    What you'll learn in this phase
    • Linux and containers. The first-minute commands for a slow node and the USE method (utilization, saturation, errors) behind them. You create each bottleneck yourself so you recognise it.
    • GPU health and diagnostics. How the NVIDIA driver reports GPU faults (XID codes), which ones mean reset, reboot or replace, and how DCGM diagnostic levels 1–3 prove a GPU is healthy.
    • LLM and training literacy. The arithmetic customers ask about: memory per parameter, KV-cache size, training FLOPs and GPU-hours. No model training, just numbers you can defend.
    • Server hardware and topology. What sits inside a multi-GPU server: CPU sockets, NUMA nodes, PCIe switches, NICs and NVLink, and how to read nvidia-smi topo -m.
    • BMC and out-of-band. Redfish, the REST API every modern server BMC exposes: power, sensors, event logs and firmware, practised on a mockup server.
    • RDMA and interconnect. What RDMA is (queue pairs, memory registration, verbs) and how to test it, using Soft-RoCE between two VMs.
    • NCCL and collectives. What NCCL does, how to run nccl-tests and why busbw (not algbw) is the number to compare with link bandwidth.
    • Slurm and provisioning. Daily Slurm: partitions, sbatch/srun/squeue/sacct, and how GPUs are declared as GRES so jobs get only the GPUs they asked for.
    • Kubernetes for GPUs. What NVIDIA's GPU Operator installs on a Kubernetes node, in what order, and how to check each piece when a GPU pod won't start.

  3. 2

    Phase 2 · Intermediate

    Practitioner

    Go deep per layer and work across nodes.

    Phase 2 is the longest and most important phase. Phase 1 showed you each layer once; now you go deep on each one and start working across nodes, which is where real clusters fail. You reproduce real failure modes on purpose and measure their effect with numbers.

    What you'll learn in this phase
    • Linux and containers. Linux depth around the GPU: flame graphs for a starved GPU, how a GPU really reaches a container (hook, device nodes, cgroups, CDI), and how to upgrade drivers safely across a fleet.
    • GPU health and diagnostics. Burn-in: hours of load while logging clocks, temperature and power, spotting throttling through clock-event reasons, and how open-source fault remediation (NVSentinel) is designed.
    • Server hardware and topology. Measuring topology: the NUMA mis-pinning penalty in numbers, and a PCIe checker for link width/speed, AER errors, ACS and IOMMU settings.
    • BMC and out-of-band. A BMC from the inside: boot real OpenBMC firmware in QEMU and talk to it with both Redfish and IPMI.
    • RDMA and interconnect. Real fabrics: bring up AWS EFA and prove NCCL uses it, InfiniBand diagnostic tools and counters, and the GPUDirect RDMA data path.
    • NCCL and collectives. Multi-node NCCL: how all-reduce scales from 1 to 2 nodes with and without the fabric, and how to diagnose a hang and a straggler.
    • Slurm and provisioning. Slurm for real: GPU nodes with containers (Pyxis/Enroot) and Node Health Check, the same cluster on three clouds, and PXE-booting bare servers into nodes.
    • Kubernetes for GPUs. Kubernetes GPU platform features: time-slicing, MPS and MIG; RDMA for pods with the Network Operator; gang scheduling and quota with Kueue on fake nodes; and Dynamic Resource Allocation.
    • Cloud, capacity and storage. What each cloud actually gives you per GPU instance: NICs, fabric, placement and limits.
    • Observability and reporting. The standard GPU metrics pipeline: dcgm-exporter → Prometheus → Grafana, with alert rules that matter.
    • LLM and training literacy. The workloads: parallelism and MFU on a real training run, checkpoint interval maths, and LLM serving metrics (TTFT, inter-token latency, throughput) with vLLM.

  4. 3

    Phase 3 · Senior

    Senior: design and operate at scale

    Turn skills into designs, automation and decisions.

    Phase 3 changes the kind of work. Instead of running tools, you produce what a solutions architect owns: designs, runbooks, automation and decisions that other people will rely on. Most labs here are free because the output is a document or code, not a measurement.

    What you'll learn in this phase
    • GPU health and diagnostics. Cluster acceptance: stages, thresholds, evidence and a go/no-go report, the document that ends a bring-up.
    • Server hardware and topology. A golden BIOS and firmware baseline, and drift detection across a fleet over Redfish.
    • BMC and out-of-band. Fleet out-of-band monitoring: BMC health across many servers, and telling cooling problems from workload problems.
    • RDMA and interconnect. Fabric design: a rail-optimised leaf-spine network for 64 nodes × 8 GPUs, cable counts, oversubscription and congestion settings.
    • NCCL and collectives. Finding one bad node among hundreds by bisection instead of testing every pair.
    • Slurm and provisioning. Slurm or Kubernetes: Slinky, Soperator and Kueue compared, written up as a decision memo.
    • Kubernetes for GPUs. Running GPUs on Kubernetes safely: automated cordon/drain/reset with a circuit breaker, a Kubebuilder operator, and a security policy pack.
    • Cloud, capacity and storage. The architect's core document: capacity, placement and wave rollout for 1,024 GPUs, plus a storage design for model loading and checkpoints.
    • Observability and reporting. Reliability analytics (bad batch, bad rack, bad driver) and executive communication drills.

  5. 4

    Phase 4 · Senior

    Capstone and proof

    One repository and one story that prove it all.

    Phase 4 turns 48 labs into one repository and one story. The capstone is a validation kit: one command builds a two-node GPU cluster with Terraform, configures it with Ansible, runs your acceptance stages and writes a dated go/no-go report, then tears everything down.

    What you'll learn in this phase
    • Capstone and proof. Packaging, automation and storytelling: one-command validation with injected failures, and public proof through posts, pull requests and a talk.

Method

Every lab follows the same loop

Learn the loop once and every lab reads the same way.

  1. 1Read

    The goal, why it matters and what done looks like.

  2. 2Bring up

    The environment named on the lab (laptop, VM, spot GPU…).

  3. 3Run

    Copy each command block in order.

  4. 4Check

    Compare with “You should see”, tick “Check yourself”.

  5. 5Fix

    Use “If it breaks”, then the debug ladder.

  6. 6Commit

    Script, results and notes into your gpu-lab repo.

  7. 7Tear down

    terraform destroy, then labdown. No idle bill.

  8. 8Say it

    Answer the interview question out loud.

Who this is for

Assumed background: comfortable with Linux, containers and Kubernetes, infrastructure as code, and at least one hyperscaler's compute and networking, plus experience delivering projects across several teams.

What it fills in: hands-on GPU diagnostics, RDMA and NCCL, PCIe/NUMA/BIOS, BMC and Redfish, bare-metal provisioning: the hardware and fabric layers a cloud background usually skips.

New to Kubernetes or Terraform? Do a short intro course on each before Phase 1; the labs assume the basics.

Built around a real job posting

Every lab maps to a requirement in NVIDIA's Solutions Architect, Infrastructure posting, so nothing is filler. The same skills apply to any GPU platform, cloud or on-prem.
