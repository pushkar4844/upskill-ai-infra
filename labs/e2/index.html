EFA on AWS, validated like a field engineer would

Bring up two EFA nodes, prove EFA is used by NCCL, and record the version matrix.

Why it matters

Knowledge of compute and networking at hyperscalers and CSPs.

Gives evidence for these requirements in the posting:

  • RDMA, congestion control, high-bandwidth interconnects
  • Stand-out: hyperscaler compute and networking knowledge

New to rdma and interconnect? Read the 5-minute primer first.

What done looks like

Deliverable. efa-versions report on two nodes and a compatibility matrix.
The outcome, step by step (field manual version)
  1. Launch two EFA-capable instances in one cluster placement group. Use a security group that allows all traffic from itself.
  2. Install the EFA software, then check fi_info -p efa -t FI_EP_RDM and ibv_devinfo on both nodes.
  3. Install the aws-ofi-nccl plugin and confirm NCCL picks it up with NCCL_DEBUG=INFO.
  4. Use the HyperPod validation script from the docs to print EFA installer, libfabric, NCCL, plugin, driver and CUDA versions. Their example shows 32 EFA interfaces on a P5-class node.
  5. Record the version matrix you ran. The doc's example pairs are illustrative; always check current release notes.

Hands-on steps

  1. Apply infra/efa2 (S9). Open sessions to both nodes.
    cd ~/gpu-lab/infra/efa2 && terraform apply && terraform output
  2. On both: EFA present?
    fi_info -p efa -t FI_EP_RDM | head
ibv_devinfo | head -20
cat /opt/amazon/efa_installed_packages 2>/dev/null | head
  3. Passwordless SSH node0 -> node1 (needed by mpirun). Allow it inside the SG only.
    # node0
ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519 && cat ~/.ssh/id_ed25519.pub
# node1: paste into ~/.ssh/authorized_keys
# node0
ssh <node1_ip> hostname
  4. Build nccl-tests with MPI on both (same path on both nodes).
    git clone https://github.com/NVIDIA/nccl-tests ~/nccl-tests && cd ~/nccl-tests
make -j MPI=1 MPI_HOME=/opt/amazon/openmpi CUDA_HOME=/usr/local/cuda NCCL_HOME=/usr/local/cuda   # adjust NCCL_HOME as in F1
  5. Run 8 ranks (4 per node) across both and confirm the EFA path in the logs.
    cat > ~/hosts <<EOF
<node0_ip> slots=4
<node1_ip> slots=4
EOF
/opt/amazon/openmpi/bin/mpirun -n 8 -N 4 --hostfile ~/hosts --bind-to none \
  -x FI_PROVIDER=efa -x NCCL_DEBUG=INFO -x LD_LIBRARY_PATH -x PATH \
  ~/nccl-tests/build/all_reduce_perf -b 8 -e 2G -f 2 -g 1 2>&1 | tee ~/efa-ar.txt
grep -iE 'NET/OFI|Selected provider|Using network' ~/efa-ar.txt | head
  6. Version matrix: EFA installer, libfabric (fi_info --version), aws-ofi-nccl, NCCL (from NCCL INFO line), driver, CUDA. Compare with the HyperPod validation doc (Go deeper).
  7. Destroy both nodes immediately after.
    terraform destroy -auto-approve
You should see. NCCL INFO lines mention NET/OFI and provider efa. busbw at large sizes clearly higher than a socket run (see F2).

If it breaks

SymptomFix
NCCL falls back to SocketCheck: aws-ofi-nccl lib on LD_LIBRARY_PATH, FI_PROVIDER=efa, SG self ingress+egress all traffic, same placement group
mpirun hangs at startSSH between nodes or hostfile IPs wrong; --mca btl_tcp_if_include <eth>

Interview

Be ready for: NCCL falls back to sockets on an EFA cluster. What are your first three checks?

Show the answer you can now give

If NCCL falls back to sockets on EFA, I check: is the aws-ofi-nccl plugin loaded (NCCL_DEBUG=INFO shows NET/OFI), does fi_info see efa, and does the security group allow all traffic to itself in both directions - plus placement group and matching versions.
