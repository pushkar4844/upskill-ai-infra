Why it matters

Strong Linux fundamentals across drivers, kernel subsystems, cgroups and containers.

Gives evidence for these requirements in the posting:

  • Linux fundamentals: drivers, kernel subsystems, cgroups, containers

New to linux and containers? Read the 5-minute primer first.

What done looks like

Deliverable. A one-page sequence diagram: container start to GPU visible, with the two failure modes you reproduced.
The outcome, step by step (field manual version)
  1. Run a CUDA container with the NVIDIA runtime. Find the OCI spec the runtime received and list the /dev/nvidia* nodes inside the container.
  2. Inspect the cgroup v2 device allow-list for that container and see which device majors are permitted.
  3. Generate a CDI spec with nvidia-ctk cdi generate and run the same container through CDI. Compare the two paths.
  4. Break it on purpose: remove one device from the allow-list, then mount mismatched driver libraries. Capture each error and the fix.

Hands-on steps

  1. On the GPU instance, run a CUDA container with Docker and look inside.
    docker run --rm --gpus all nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04 bash -c 'ls -l /dev/nvidia*; nvidia-smi -L; mount | grep -i nvidia | head'
  2. See the runtime config and the OCI spec the runtime got.
    cat /etc/docker/daemon.json
nvidia-ctk --version
CID=$(docker run -d --gpus all nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04 sleep 600)
sudo cat /run/containerd/io.containerd.runtime.v2.task/moby/$CID/config.json | jq '.linux.devices, .hooks' | head -60
  3. cgroup v2 device control (eBPF): look at the container's cgroup.
    cat /proc/$(docker inspect -f '{{.State.Pid}}' $CID)/cgroup
ls -l /dev/nvidia* | awk '{print $5,$6,$10}'   # major,minor numbers
  4. Generate a CDI spec and run through CDI instead of the hook.
    sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
nvidia-ctk cdi list
docker run --rm --device nvidia.com/gpu=all nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi -L   # needs Docker 25+ with CDI enabled
  5. Break it twice and capture each error: (1) run without --gpus; (2) bind-mount a wrong libnvidia-ml version into the container.
    docker run --rm nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi    # error 1
# error 2: docker run --rm --gpus all -v /path/to/other/libnvidia-ml.so.1:/usr/lib/x86_64-linux-gnu/libnvidia-ml.so.1 ... nvidia-smi
You should see. Inside the container: /dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm and driver libs mounted from the host. The OCI spec shows the hook (legacy) or CDI-injected devices.

Interview

Be ready for: Walk me through what happens between kubectl apply and a GPU appearing inside the pod.

Show the answer you can now give

kubectl apply -> scheduler picks a node with nvidia.com/gpu -> kubelet asks the device plugin for a GPU -> containerd starts the container through the NVIDIA runtime or CDI, which adds /dev/nvidia* nodes, the cgroup device allow rules and the host driver libraries.
