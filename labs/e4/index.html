Why it matters

Congestion control and high-bandwidth interconnects; leadership across multi-team infrastructure challenges.

Gives evidence for these requirements in the posting:

  • RDMA, congestion control, high-bandwidth interconnects

New to rdma and interconnect? Read the 5-minute primer first.

What done looks like

Deliverable. A three-page design doc with a bill-of-materials table.
The outcome, step by step (field manual version)
  1. Assume 64 nodes with 8 GPUs and 8 compute NICs each. State your switch radix and link speed explicitly.
  2. Lay out a rail-optimized leaf-spine fabric. Compute leaf count, spine count, uplinks and cable count for 1:1 and 2:1 oversubscription.
  3. Compare with the DGX SuperPOD reference architecture. Note where and why you differ.
  4. Describe PFC, ECN and DCQCN at concept level and where each is configured in a RoCE design versus InfiniBand's credit-based flow control.
  5. Show how topology reaches the schedulers (Topograph for Slurm and Kubernetes) so jobs are placed close together.

Hands-on steps

  1. Assumptions: 64 nodes, 8 GPUs and 8 x 400G NICs each (one NIC per GPU), switch radix 64 ports of 400G. Write them down first.
  2. Rail-optimized: NIC k of every node goes to leaf group 'rail k'. 64 nodes x 8 NICs = 512 endpoints. With 64-port leaves at 1:1, each leaf uses 32 down + 32 up -> 16 leaves; spine ports needed = 16 x 32 = 512 -> 8 spines of 64 ports. Recompute for 2:1.
  3. Bill of materials: leaves, spines, NIC-leaf cables (512), leaf-spine cables, optics. Compare with the DGX SuperPOD reference architecture (scalable units of 32 nodes) and explain differences.
  4. Congestion control: InfiniBand credit-based flow control vs RoCE with PFC + ECN + DCQCN; where each is configured; risks (PFC storms, head-of-line blocking).
  5. How topology reaches schedulers: NVIDIA Topograph -> Slurm topology.conf / Kubernetes labels, so jobs land in the same leaf/rail domain.
You should see. 3-page design doc with diagrams and BOM table.

Interview

Be ready for: Why does a 1,024-GPU job want a rail-optimized network?

Show the answer you can now give

Rail-optimized means GPU k on every node talks through rail k, so the same-rank traffic of all-reduce stays one hop on a leaf; cross-rail traffic goes over NVLink inside the node. Fewer hops, less congestion, predictable bandwidth.
