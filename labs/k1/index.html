Why it matters

Familiarity with modern deep learning, LLM architectures and distributed training or inference challenges at scale.

Gives evidence for these requirements in the posting:

  • Stand-out: LLM and distributed training literacy

New to llm and training literacy? Read the 5-minute primer first.

What done looks like

Deliverable. A notebook of worked examples.
The outcome, step by step (field manual version)
  1. Read the scaling book chapters on roofline, transformer math, parallelism and the GPU chapter.
  2. Compute memory for a 70B model in BF16 for weights, gradients and Adam states, then decide what fits on 8 x 80 GB GPUs.
  3. Compute KV cache size per token for a model you pick and see how context length changes batch size.
  4. Estimate training FLOPs with 6 x parameters x tokens and turn it into GPU-days at a stated MFU.
  5. Build a tiny GPT from the Karpathy walkthrough so the terms stop being abstract.

Hands-on steps

  1. Create a notebook environment.
    cd ~/gpu-lab/llm && python3 -m venv .venv && . .venv/bin/activate && pip install jupyterlab
jupyter lab --no-browser   # open the printed http://localhost:8888 URL in Windows browser
  2. Cell 1 - training memory (mixed precision + Adam). Rule of thumb: ~16 bytes per parameter (BF16 weights 2 + BF16 grads 2 + FP32 master 4 + Adam m 4 + v 4), activations extra.
    P = 70e9
bytes_per_param = 2 + 2 + 4 + 4 + 4
total_gb = P * bytes_per_param / 1e9
print(f'{total_gb:,.0f} GB total')                 # ~1,120 GB
for gpus in (8, 16, 32):
    print(gpus, 'GPUs fully sharded ->', round(total_gb/gpus), 'GB/GPU (80 GB cards)')
  3. Cell 2 - KV cache per token = 2 (K and V) x layers x kv_heads x head_dim x bytes. Example Llama-3-8B-like: 32 layers, 8 KV heads, head_dim 128, BF16.
    layers, kv_heads, head_dim, b = 32, 8, 128, 2
per_token = 2 * layers * kv_heads * head_dim * b
print(per_token/1024, 'KiB per token')              # 128 KiB
ctx = 8192
print(per_token*ctx/2**30, 'GiB per 8k-token sequence') # 1 GiB
free_gb = 24 - 16   # e.g. A10G 24 GB minus ~16 GB weights
print('max concurrent 8k sequences ~', int(free_gb*2**30 // (per_token*ctx)))
  4. Cell 3 - training compute: FLOPs ~ 6 x params x tokens. Convert to GPU-days at a given MFU.
    N, D = 8e9, 1e12
flops = 6 * N * D                  # 4.8e22
peak = 989e12                      # H100 dense BF16 FLOP/s (spec sheet)
mfu = 0.40
gpu_days = flops / (peak*mfu) / 86400
print(f'{gpu_days:,.0f} GPU-days -> {gpu_days/1024:.1f} days on 1,024 GPUs')
  5. Read the two books linked in Go deeper (JAX scaling book: roofline + transformer chapters; HF Ultra-Scale Playbook). Add one markdown cell per chapter: 3 bullets in your own words.
  6. Optional: watch Karpathy's build-nanogpt walkthrough; run it later on a GPU instance so the words 'attention', 'layer', 'token' become concrete.
    git clone https://github.com/karpathy/build-nanogpt
You should see. 70B needs ~1.1 TB for training state, so it does not fit on one 8x80 GB node without offload; KV cache for an 8B-class model is ~128 KiB/token; 8B x 1T tokens ~1,400 H100-days at 40% MFU.

Show the answer you can now give

Can a 70B model train on one 8x80 GB node? Show the 16 bytes/param math: ~1.1 TB of state vs 640 GB HBM - not without offload or more nodes. For inference I size KV cache per token and back out max batch at a context length.
