Slurm in Docker with fake GPUs

Slurm is the HPC scheduler used for most large training clusters. Learn the daily commands and how GPUs are declared (GRES) on a laptop.

Why it matters

JD stand-out and role context: SLURM and Kubernetes for distributed workloads.

New to slurm and provisioning? Read the 5-minute primer first.

What done looks like

Deliverable. A compose file and an sbatch cookbook.
The outcome, step by step (field manual version)
  1. Bring up a Slurm cluster in containers and run sinfo, squeue, sbatch, srun, sacct.
  2. Add a gres entry that emulates GPUs in gres.conf and request them with --gres=gpu:2.
  3. Enable cgroup constraints and show a job cannot see devices it was not given.
  4. Write a simple prolog script that fails a node when a check returns non-zero.

Hands-on steps

  1. Clone and start the cluster. Version 3.0 of the repo uses make targets and offers a prebuilt image.
    cd ~/gpu-lab/slurm && git clone https://github.com/giovtorres/slurm-docker-cluster && cd slurm-docker-cluster
cp .env.example .env
make build        # or pull the prebuilt image (see README for the tag step)
make up
make status
  2. Daily commands, from a shell on the controller.
    make shell        # opens a shell in slurmctld
sinfo
srun -N2 hostname
sbatch --wrap='sleep 60; hostname' -N1
squeue
scontrol show job <id>
scancel <id>
sacct --format=JobID,JobName,State,Elapsed,NodeList
make run-examples # the repo's sample jobs
  3. Declare fake GPUs. Edit the config in the repo's config/<version>/ folder, push it into the running cluster, and create fake device files on each compute container (c1, c2).
    # config/<version>/slurm.conf
GresTypes=gpu
NodeName=c[1-2] ... Gres=gpu:2          # append Gres=gpu:2 to the existing NodeName line

# config/<version>/gres.conf
NodeName=c[1-2] Name=gpu File=/dev/nvidia[0-1]

docker exec c1 bash -c 'touch /dev/nvidia0 /dev/nvidia1'
docker exec c2 bash -c 'touch /dev/nvidia0 /dev/nvidia1'
make update-slurm FILES="slurm.conf gres.conf"
make reload-slurm
docker exec slurmctld scontrol show node c1 | grep -i gres
  4. Request GPUs and see what the job gets.
    srun --gres=gpu:1 bash -c 'echo CUDA_VISIBLE_DEVICES=$CUDA_VISIBLE_DEVICES'
srun --gres=gpu:2 bash -c 'echo CUDA_VISIBLE_DEVICES=$CUDA_VISIBLE_DEVICES'
sbatch --gres=gpu:3 --wrap=hostname     # should stay pending / be rejected: no node has 3
  5. Write a tiny prolog health check (concept for G2): a script that exits non-zero drains the node.
    cat > prolog.sh <<'EOF'
#!/bin/bash
# fail if expected GPU device files are missing
for d in /dev/nvidia0 /dev/nvidia1; do [ -e $d ] || { echo "missing $d"; exit 1; }; done
exit 0
EOF
# add Prolog=/path/prolog.sh to slurm.conf, restart, then delete /dev/nvidia1 on c2 and submit a job - c2 should drain
# sinfo -R shows the reason
  6. Optional, on a machine with an NVIDIA GPU: the repo can add a real GPU worker (g1). Set GPU_ENABLE=true in .env, then run make rebuild and make test-gpu.
You should see. sinfo shows partition with 2 nodes idle. srun --gres=gpu:1 prints CUDA_VISIBLE_DEVICES=0. A 3-GPU request cannot run. After breaking c2's device file, c2 goes DRAIN.

Interview

Be ready for: How does Slurm keep one job's GPUs invisible to another?

Show the answer you can now give

Slurm declares GPUs as GRES in gres.conf; with cgroup device constraints a job sees only the GPUs it was allocated, exposed via CUDA_VISIBLE_DEVICES. Prolog/epilog health checks drain bad nodes before jobs land on them.
