Flame-graph a stalled GPU job

GPU at 40% usually means the GPU is waiting for the CPU. Prove it with a flame graph, fix it, prove the fix.

Where
G1 One GPU, spot (g4dn.xlarge T4 16 GB or g5.xlarge A10G 24 GB)
Time
6 hours

~$1-2

Why it matters

Identify performance bottlenecks at node, accelerator and application layers.

Gives evidence for these requirements in the posting:

  • Linux tools: dmesg, journalctl, lspci, numactl, ethtool, iostat, perf, nvidia-smi, ipmitool
  • Find bottlenecks at cluster, node, accelerator, network, application layers

New to linux and containers? Read the 5-minute primer first.

What done looks like

Deliverable. Before/after flame graphs with the GPU utilization chart and a three-line root cause.
The outcome, step by step (field manual version)
  1. Run a small PyTorch training loop with a deliberately slow dataloader (num_workers=0). Watch SM utilization dip in nvidia-smi dmon.
  2. Capture CPU stacks: perf record -F 99 -a -g -- sleep 30, then perf script | stackcollapse-perf.pl | flamegraph.pl > cpu.svg.
  3. Load the same capture into FlameScope to see sub-second stalls that a flame graph averages away.
  4. Fix the dataloader (workers, pin_memory, prefetch) and capture again. Show before and after side by side with GPU utilization.

Hands-on steps

  1. GPU instance + profiling tools.
    terraform apply   # in infra/gpu1
sudo apt install -y linux-tools-$(uname -r) linux-tools-common
git clone https://github.com/brendangregg/FlameGraph ~/FlameGraph
python3 -m venv ~/venv && . ~/venv/bin/activate && pip install torch torchvision
  2. A training loop with a deliberately slow dataloader.
    cat > slow.py <<'EOF'
import time, torch, torchvision, torchvision.transforms as T, sys
W = int(sys.argv[1]) if len(sys.argv) > 1 else 0
ds = torchvision.datasets.FakeData(size=20000, image_size=(3,224,224), transform=T.Compose([T.RandomResizedCrop(224), T.ToTensor()]))
dl = torch.utils.data.DataLoader(ds, batch_size=64, num_workers=W, pin_memory=W>0, prefetch_factor=4 if W else None)
m = torchvision.models.resnet50().cuda(); opt = torch.optim.SGD(m.parameters(), 0.1)
t = time.time()
for i, (x, y) in enumerate(dl):
    x, y = x.cuda(non_blocking=True), y.cuda(non_blocking=True)
    loss = torch.nn.functional.cross_entropy(m(x), y); opt.zero_grad(); loss.backward(); opt.step()
    if i % 20 == 0: print(i, f'{(time.time()-t)/20:.3f}s/step', flush=True); t = time.time()
    if i == 200: break
EOF
python3 slow.py 0 &          # num_workers=0
nvidia-smi dmon -s u -c 30   # watch 'sm' column dip
  3. Capture CPU stacks while it runs.
    sudo perf record -F 99 -a -g -- sleep 30
sudo perf script | ~/FlameGraph/stackcollapse-perf.pl | ~/FlameGraph/flamegraph.pl > cpu_before.svg
  4. Fix: more workers, pinned memory, prefetch. Measure again.
    python3 slow.py 8 & nvidia-smi dmon -s u -c 30
sudo perf record -F 99 -a -g -- sleep 30 && sudo perf script | ~/FlameGraph/stackcollapse-perf.pl | ~/FlameGraph/flamegraph.pl > cpu_after.svg
  5. Optional: load the perf data into Netflix FlameScope to see sub-second stalls; try PyTorch profiler (kineto) for a GPU timeline.
You should see. Before: GPU sm% low/spiky, flame graph dominated by PIL/transform functions in the main Python process, slow s/step. After: higher steady sm%, faster steps, work spread over worker processes.

Interview

Be ready for: GPU utilization is 40%. How do you decide whether the problem is CPU-side or GPU-side?

Show the answer you can now give

If GPU util is low I check whether the GPU is starved: CPU flame graph, dataloader workers, host-to-device copies, then GPU-side kernels with a profiler. Here the fix was more dataloader workers and pinned memory.
