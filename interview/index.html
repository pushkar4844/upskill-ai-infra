Interview bank

Short answers to know cold

Xid 79

The GPU has fallen off the bus: it is no longer reachable over PCIe. NVIDIA's catalog says restart the bare-metal host and contact support, since it often points to a PCIe link or hardware failure.

Xid 48, 63, 64

48 is an uncorrectable double-bit ECC error. 63 records a row-remapping event and is informational. 64 is a row-remap failure and needs a GPU reset or escalation.

algbw versus busbw

algbw is size divided by time. busbw applies a correction so the number is comparable to link bandwidth regardless of rank count: all-reduce multiplies by 2(n-1)/n.

DCGM r3 versus r2

r3 adds the diagnostic, targeted stress, targeted power, NVBandwidth and NCCL plugins on top of r2's software, PCIe and NVLink, memory and memory bandwidth tests.

GPUDirect RDMA requirements

GPU and NIC under the same upstream PCIe root complex for good performance; IOMMU disabled or pass-through; peer memory module loaded.

Multi-node all-reduce bar

One public guide uses roughly 92% of theoretical fabric bandwidth as the pass line, for example 370 GB/s on a 400 GB/s fabric. State your own threshold and why.

Remediation loop

Use a circuit breaker so a cluster-wide event cannot cordon every node. Reset one GPU when the fault is recoverable; reboot the node only when needed.

Pass/fail semantics

Define thresholds in a file. A job that finishes but misses its target is still a failure.

One question per lab

1 Phase 1 · Foundations

A1A node is slow. What do you run first, second and third, and what does each rule out?

A node is slow. I run uptime, dmesg, vmstat, mpstat, pidstat, iostat, free, sar -n DEV in that order - USE method: utilization, saturation, errors per resource - and on a GPU box add nvidia-smi and clock-event reasons. Each one rules out a layer in seconds.

B1Xid 79 appears in dmesg. What does it mean and what do you do? How does it differ from Xid 48 followed by 63 or 64?

XID 79 means the GPU dropped off PCIe - drain and reboot, check power/PCIe, escalate. 48 is an uncorrectable ECC error; 63 is a row-remap event that applies at next reset; 64 means the remap failed. I built a decoder that turns those log lines into actions.

K1Can a 70B model train on one 8 x 80 GB node? Show your math.

Can a 70B model train on one 8x80 GB node? Show the 16 bytes/param math: ~1.1 TB of state vs 640 GB HBM - not without offload or more nodes. For inference I size KV cache per token and back out max batch at a context length.

Open lab K1 →

C1Draw an 8-GPU HGX node: GPUs, NVSwitches, NICs, CPUs. Where does GPUDirect RDMA traffic flow?

On an HGX H100 node 8 GPUs connect through NVSwitch, each GPU pairs with a NIC under the same PCIe switch, split across two CPU sockets. GPUDirect RDMA traffic goes GPU->PCIe switch->NIC without touching CPU memory, so placement under the same switch matters.

Open lab C1 →

B2What does dcgmi diag -r 3 run that -r 2 does not, and when would you pay for -r 4 ?

r1 is a seconds-long sanity check, r2 adds PCIe/NVLink and memory tests, r3 adds stress, power, bandwidth and NCCL plugins and takes ~30 min on 8 GPUs, r4 adds memtest/pulse for hours. I run r3 at acceptance and r1 at job start.

Open lab B2 →

D1IPMI versus Redfish: what changed and why do hyperscalers prefer Redfish?

IPMI is an old binary protocol with weak security and vendor quirks; Redfish is HTTPS + JSON with a schema, sessions and eventing, so hyperscalers automate fleets with it - inventory, power, thermal, logs and firmware updates from one API.

Open lab D1 →

E1Explain RDMA to a cloud engineer in 60 seconds. Why does it matter for all-reduce?

RDMA moves data NIC-to-memory without the remote CPU or kernel copies, using queue pairs and registered memory regions. All-reduce sends huge buffers between GPUs every step, so the fabric must be RDMA (IB, RoCE or EFA) or the GPUs sit idle.

Open lab E1 →

F1What is the difference between algbw and busbw, and why does busbw exist?

algbw is bytes over time; busbw multiplies by 2(n-1)/n for all-reduce so it reflects per-link traffic and is comparable to hardware bandwidth regardless of GPU count. I compare large-message busbw to the NVLink or NIC line rate.

Open lab F1 →

G1How does Slurm keep one job's GPUs invisible to another?

Slurm declares GPUs as GRES in gres.conf; with cgroup device constraints a job sees only the GPUs it was allocated, exposed via CUDA_VISIBLE_DEVICES. Prolog/epilog health checks drain bad nodes before jobs land on them.

Open lab G1 →

H1What does the GPU Operator install and in what order?

The GPU Operator installs driver (optional), container toolkit, device plugin, GPU feature discovery, DCGM exporter and validators as DaemonSets. The device plugin advertises nvidia.com/gpu; when a pod requests it, kubelet allocates a GPU and the NVIDIA runtime injects the device nodes and driver libraries.

2 Phase 2 · Practitioner

A2GPU utilization is 40%. How do you decide whether the problem is CPU-side or GPU-side?

If GPU util is low I check whether the GPU is starved: CPU flame graph, dataloader workers, host-to-device copies, then GPU-side kernels with a profiler. Here the fix was more dataloader workers and pinned memory.

Open lab A2 →

A3Walk me through what happens between kubectl apply and a GPU appearing inside the pod.

kubectl apply -> scheduler picks a node with nvidia.com/gpu -> kubelet asks the device plugin for a GPU -> containerd starts the container through the NVIDIA runtime or CDI, which adds /dev/nvidia* nodes, the cgroup device allow rules and the host driver libraries.

Open lab A3 →

A4You roll a driver upgrade across 500 nodes. What are your gates and your rollback trigger?

Fleet driver upgrade: canary 1% -> drain -> upgrade driver, toolkit and Fabric Manager together -> reboot -> DCGM r1 + NCCL smoke -> uncordon; stop and roll back if any gate fails or XIDs rise in the canary.

Open lab A4 →

B3How long do you burn in a new node and what usually fails first?

I burn in for hours with gpu-burn plus a memory test, log clocks/temp/power/event reasons per second, and fail a GPU for uncorrectable ECC, sustained HW slowdown, or clocks well below the median of its peers.

Open lab B3 →

B4A node reports a recoverable GPU fault. Reset the GPU or reboot the node, and how do you decide?

Recoverable fault (e.g. XID 63, 94): drain and reset the GPU at a safe point. Bus or firmware faults (79, 119): reboot the node. Repeats on the same GPU or row-remap failures: RMA. A circuit breaker stops remediation when too many nodes fail at once - that's a fleet problem, not a node problem.

Open lab B4 →

C2Why does CPU socket placement matter for a GPU and a NIC?

A GPU and its NIC hang off one socket's PCIe root. If the process and its memory live on the other socket, every copy crosses the inter-socket link, cutting bandwidth and adding latency - so we bind ranks to the local NUMA node and NIC.

Open lab C2 →

C3A GPU shows half the expected PCIe bandwidth. What do you check?

Half PCIe bandwidth: compare LnkCap vs LnkSta under load for width/gen downtraining, check AER errors and dmesg, reseat/swap riser or cable, check BIOS link settings, then re-measure with nvbandwidth.

Open lab C3 →

D2What does a BMC do when the host OS is hung?

The BMC is a separate small computer on the board with its own network. When the host OS hangs, it still reports sensors and logs and can power-cycle the host, give a serial console and update firmware.

Open lab D2 →

E2NCCL falls back to sockets on an EFA cluster. What are your first three checks?

If NCCL falls back to sockets on EFA, I check: is the aws-ofi-nccl plugin loaded (NCCL_DEBUG=INFO shows NET/OFI), does fi_info see efa, and does the security group allow all traffic to itself in both directions - plus placement group and matching versions.

Open lab E2 →

E3A link has a rising symbol error counter. What do you do before you replace the cable?

Rising symbol errors: check the counter rate after clearing, look at both ends, reseat/clean the cable, check the transceiver temperature/power, swap ports to see if the error follows the cable or the port, then replace.

Open lab E3 →

E5What must be true for GPUDirect RDMA to be fast on a given server?

GPUDirect RDMA needs the GPU and NIC under the same PCIe root complex (ideally same switch), IOMMU off or passthrough, ACS not forcing traffic up to the root, and the peer-memory module loaded.

Open lab E5 →

F2busbw drops from 2 nodes to 4. Where do you look?

busbw drops 2->4 nodes: check whether the job crossed a spine (topology/placement), per-NIC errors and congestion counters, a straggler node (F4 bisection), NCCL picking the wrong NIC/algorithm, then rail alignment.

Open lab F2 →

F3A 64-GPU job hangs after 4 hours. How do you find the cause?

Hang after hours: find which rank stopped (NCCL_DEBUG, flight recorder, py-spy dumps), check that node's dmesg for XIDs, NIC errors and OOM, check for a straggler via per-rank step times, then bisect nodes if it's fabric.

Open lab F3 →

G2Which health checks would you run at job start versus continuously?

At job start (prolog) I run fast checks: GPU count, no new XIDs, driver loaded, DCGM r1. Continuously (NHC every few minutes): ECC, NIC link state, filesystem mounts, temps. Weekly or on idle: DCGM r3 and NCCL bisection.

Open lab G2 →

G3Compare how three clouds expose the GPU fabric to a customer.

AWS exposes EFA via libfabric + aws-ofi-nccl, Azure uses InfiniBand on HB/ND VMs, Google uses its own GPU NICs/GPUDirect variants per machine type - so NCCL plugins, tuning and health checks differ even with the same GPU.

Open lab G3 →

G5Walk me through how a bare-metal server becomes a Slurm or Kubernetes node.

Racked server -> BMC powers it on via Redfish -> PXE/DHCP gives an iPXE script -> kernel and image load -> config management installs driver/OFED/agents -> burn-in and validation -> node joins Slurm or Kubernetes.

Open lab G5 →

H2A tenant needs hard isolation on one GPU. Time-slicing, MPS or MIG, and why?

Hard isolation for a tenant on one GPU: MIG - dedicated memory slices and SMs with fault isolation. Time-slicing and MPS share memory and can interfere, fine for dev or small inference.

Open lab H2 →

H3How does a pod get access to an RDMA NIC?

The Network Operator installs the NIC driver, a device plugin that advertises RDMA resources (shared or SR-IOV VFs), and Multus for a secondary network; the pod requests the RDMA resource and attaches the secondary interface, so NCCL can use RDMA from inside the pod.

Open lab H3 →

H4Two teams share 256 GPUs. How do you enforce quota and keep gangs from deadlocking?

Quota per team with ClusterQueues and a cohort for borrowing; all-or-nothing admission (gang) so partial jobs don't hold GPUs and deadlock; topology labels so gangs land in one rack or NVLink domain.

Open lab H4 →

H5Why is DRA better than the device plugin model for NVLink-connected GPUs?

Device plugins only say 'N GPUs'. DRA publishes device attributes and lets a claim select with CEL (model, memory, NVLink domain), share devices and allocate groups - which matters for NVLink-connected GPUs across nodes.

Open lab H5 →

I1Why do two clouds with the same GPU deliver different all-reduce numbers?

Same GPU, different all-reduce: NIC count and speed per GPU, fabric type and NCCL plugin, rail-optimized vs not, placement (same spine or not), and tuning defaults.

Open lab I1 →

J1Which three GPU metrics do you alert on, and why not utilization alone?

I alert on XID errors, uncorrectable ECC / row-remap failures, missing GPUs, thermal/power throttling and NVLink errors - utilization alone tells you nothing about health.

Open lab J1 →

K2MFU is 25%. Name three places you would look.

MFU 25%: check data loading/CPU stalls, communication not overlapped (busbw vs needed), wrong parallelism for the interconnect (TP over PCIe), small micro-batches, and kernels not using tensor cores (precision).

Open lab K2 →

K3How often should a 4,096-GPU job checkpoint?

Checkpoint interval comes from checkpoint cost and job MTBF (Young/Daly). A 4,096-GPU job has a short MTBF, so I want async/local checkpoints that cost seconds, which lets me checkpoint every few minutes.

Open lab K3 →

K4What does a customer need in their network before they try disaggregated serving?

Disaggregated serving moves KV cache from prefill to decode GPUs, so the customer needs a high-bandwidth RDMA path between those pools (NIXL over IB/RoCE/EFA), sensible topology placement and enough HBM for the KV working set.

3 Phase 3 · Senior: design and operate at scale

B5How do you validate a new 256-GPU cluster before handing it to the customer?

New 256-GPU cluster: inventory and firmware/driver baseline, DCGM r3 and burn-in per node, single-node NCCL over NVLink, NIC/RDMA tests, then all-reduce at pair, rack and full scale against a threshold like ~92% of fabric bandwidth, storage and a reference training run - with a signed report and defect log.

Open lab B5 →

C4How would you detect and fix BIOS drift across 2,000 servers?

Pull BIOS attributes and firmware inventory over Redfish from every BMC, diff against a golden per platform, alert on drift, and remediate with Redfish Bios/Settings in rolling maintenance windows - gated by validation after reboot.

Open lab C4 →

D3Rack 14 has hot GPUs. How do you prove it is cooling and not workload?

Rack 14 hot GPUs: compare BMC inlet temps and fan speeds across the rack with GPU temps and power from DCGM. Inlet high for all nodes = cooling; inlet normal but GPU hot at the same power = that GPU/heatsink; high power = workload.

Open lab D3 →

E4Why does a 1,024-GPU job want a rail-optimized network?

Rail-optimized means GPU k on every node talks through rail k, so the same-rank traffic of all-reduce stays one hop on a leaf; cross-rail traffic goes over NVLink inside the node. Fewer hops, less congestion, predictable bandwidth.

Open lab E4 →

F4One node out of 200 slows every all-reduce. How do you find it without testing all 200 pairs?

One slow node in 200: split into groups, run all-reduce per group, recurse into groups below threshold, confirm suspects paired with known-good nodes - about log2(N) rounds instead of N-squared pairs, then drain the node and check its XIDs, NIC counters and PCIe.

Open lab F4 →

G4A customer asks Slurm or Kubernetes for training. How do you answer?

Researchers who live in sbatch: keep Slurm, maybe run it on K8s (Slinky/Soperator) to share infra. Platform teams serving and training on one fleet: K8s with Kueue/KAI for quota and gang scheduling. Topology awareness is required either way.

Open lab G4 →

H6How do you avoid a remediation loop that drains your whole cluster?

Detection (NPD/DCGM) sets node conditions; a remediator cordons, drains and resets or reboots; a circuit breaker (maxUnhealthy) stops automation during fleet-wide events so it can't take down the cluster.

Open lab H6 →

H7Describe a reconcile loop and how you make it idempotent.

A reconcile loop reads desired state (spec) and actual state, makes one step toward desired, writes status and requeues. Idempotent = deterministic names, create-if-absent, owner references, safe to run any number of times.

Open lab H7 →

H8How do you stop a tenant from running a privileged container on your GPU nodes?

Stop privileged containers on GPU nodes with admission policy (Kyverno/Gatekeeper) allowing exceptions only for the operator namespace, plus runtime detection with Falco and image scanning in CI.

Open lab H8 →

I2You have 4 weeks to bring up 1,024 GPUs for a customer. What is your plan?

4 weeks to 1,024 GPUs: secure capacity and placement first, golden image and driver matrix, fabric validation, then waves of 128 -> 256 -> 640 GPUs each gated by acceptance tests and health automation, with a spare pool and daily exec status on risks and decisions.

Open lab I2 →

I3A 70B model takes 12 minutes to load on each scale-out. How do you cut it?

70B model taking 12 min per scale-out: pre-stage weights on local NVMe or a node-local cache, stream with a parallel loader, use a parallel FS or high-throughput object access with many connections, and keep images slim so pull time doesn't add up.

Open lab I3 →

J2How do you tell a bad GPU batch from a bad rack?

Bad batch: failures follow serial/lot numbers across many racks. Bad rack: failures cluster by location across batches - usually power, cooling or a switch. Cohort by both and the pattern separates them.

Pick one real project with several teams and no direct authority (for example a multi-account cloud migration with DR drills). Explain how you created clarity: one runbook, one status format, clear owners and dates, and what changed because of it.

4 Phase 4 · Capstone and proof

L1Walk me through your validation kit: what it checks, what it caught, what it cost.

My kit builds a 2-node EFA cluster with Terraform, configures it with Ansible, runs DCGM, burn-in, NCCL single and multi-node, RDMA and storage stages against thresholds in a criteria file, and writes a go/no-go report. It caught EFA fallback, a power-capped straggler and a NUMA mis-binding; a run costs about $20.
