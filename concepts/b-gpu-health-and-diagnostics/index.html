Concept primer

GPU health and diagnostics

GPU health is read from three places: kernel XID errors, ECC and row-remapping counters, and active diagnostics (DCGM, burn-in). Fleets combine passive monitoring with scheduled active tests.

Key ideas

  1. XID errors are the driver's error codes in the kernel log (NVRM: Xid ...). Some point to the application (13, 31, 43), some to memory (48, 63, 64, 92, 94, 95), NVLink (74), the PCIe bus (79) or GPU firmware (119, 120).
  2. ECC: single-bit errors are corrected; double-bit errors are not. Modern data-center GPUs replace bad memory rows with row remapping, which takes effect after a GPU reset.
  3. DCGM diagnostic levels: r1 is a seconds-long sanity check, r2 adds PCIe/NVLink and memory tests, r3 adds stress, power, bandwidth and NCCL plugins, r4 adds long memory tests. Use r1 at job start and r3 at acceptance.
  4. Burn-in means hours of load while logging temperature, power, clocks and clock-event (throttle) reasons. Weak GPUs show up as clocks below their peers, not only as crashes.
  5. Remediation ladder: reset the GPU, reboot the node, then RMA. Automation needs a circuit breaker so a fleet-wide event doesn't drain the whole cluster.

Common mistakes

  • Alerting on utilization instead of errors
  • Treating XID 63 (informational) like XID 79 (critical)
  • Remediating automatically with no limit on how many nodes can be drained at once

What interviewers probe

XID 79 appears in dmesg: what does it mean and what do you do? What does DCGM r3 add over r2?

Practise it

  1. B1Build an XID decoderXID errors are how the NVIDIA driver reports GPU problems in the kernel log. You will build a tool that reads them and tells an operator what to do. No GPU needed. Phase 1Core5 hL
  2. B2DCGM diagnostics, levels 1 to 4DCGM is NVIDIA's data-center GPU manager. Its diag levels are how fleets prove a GPU is healthy. Learn what each level runs and how long it takes. Phase 1Core6 hG1
  3. B3Burn-in and thermal or power throttlingNew GPUs are stressed for hours before customers get them. Learn to burn in, log clocks/temps/power, and spot throttling. Phase 2Core8 hG1
  4. B4Automated quarantine with NVSentinel (exploratory)Read and run NVIDIA's open-source fault detection + remediation system. Understand the design even if you can't trigger real hardware faults. Phase 28 hG1
  5. B5Write the cluster acceptance runbookThe document a customer signs before taking a GPU cluster: stages, thresholds, evidence, go/no-go. Your strongest interview artifact. Phase 3Core16 hG2N

In the job posting

  • Bring-up and validation of multi-GPU and multi-node NVIDIA platforms
  • CUDA, NCCL, NVSwitch/NVLink, drivers, performance tuning
  • Server hardware: PCIe, firmware, NUMA, BIOS/UEFI, power and thermal
  • Stand-out: pilot to high-volume deployment record

Terms

Burn-in
Hours of stress on new hardware while logging temperature, power, clocks and errors, to catch early failures before customers do.
Clock-event reasons
nvidia-smi fields explaining why GPU clocks are lowered (power cap, thermal, hardware slowdown). Formerly called throttle reasons.
DCGM
NVIDIA Data Center GPU Manager: health, diagnostics (levels r1-r4), policy and telemetry for data-center GPUs.
ECC
Error-correcting code memory. Single-bit errors are corrected; double-bit (uncorrectable) errors kill the affected work.
Row remapping
Replacing bad GPU memory rows with spares; pending remaps apply after a GPU reset (XID 63 event, XID 64 failure).
XID
NVIDIA driver error code written to the kernel log as 'NVRM: Xid'.
