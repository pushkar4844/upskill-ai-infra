Concept primer

BMC and out-of-band

The BMC is a small independent computer on the server board. It lets you see and control the machine when the OS is down, which is most of early bring-up.

Key ideas

  1. The BMC has its own network port and power. It reports sensors (temperature, fans, power supplies), keeps the System Event Log (SEL), gives a serial console and can power-cycle the host.
  2. IPMI is the older binary protocol. Redfish is HTTPS + JSON with a published schema, sessions and eventing, which is why large fleets automate with it.
  3. Redfish tree: /redfish/v1/Systems (the host), Chassis (thermal, power), Managers (the BMC), UpdateService (firmware), with LogServices for event logs.
  4. Fleet hygiene: one golden BIOS/firmware baseline per platform, drift detection over Redfish, staged remediation in maintenance windows.
  5. OCP's diagnostic output format standardises test results across vendors, the kind of detail hyperscaler hardware teams care about.

Common mistakes

  • Leaving default BMC credentials or exposing BMCs on a routable network
  • Assuming attribute names are the same across server vendors
  • Reading GPU temperatures without inlet temperatures (cooling vs workload)

What interviewers probe

IPMI vs Redfish: what changed and why? Rack 14 has hot GPUs: how do you prove it is cooling and not workload?

In the job posting

  • Linux tools: dmesg, journalctl, lspci, numactl, ethtool, iostat, perf, nvidia-smi, ipmitool
  • BMC, IPMI, Redfish, out-of-band debugging

Terms

BMC
Baseboard Management Controller: an independent controller on the server board for sensors, logs, console and power control.
IPMI
Older binary protocol for out-of-band server management; largely superseded by Redfish.
Redfish
DMTF standard REST/JSON API for server management exposed by BMCs.
SEL
System Event Log kept by the BMC: power, thermal and hardware events.
